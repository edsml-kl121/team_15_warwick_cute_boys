Recommendation agent architecture

Both presenter actions share guest context and chat delivery. Each branch builds its own candidates and calls a different Shopee tool.

Where each decision lives

Guest and session
presenter_trigger checks the presenter key. It matches display names case-insensitively, then runs once per matching guest ID. Each run targets that guest’s most recently updated session, with presenter as the default. Presenter route · Guest lookup
Data and selection
load_recommendation_context refreshes MongoDB data by guest ID and can load a bucket persona if history is missing. choose uses the first candidate without a model. With a model configured, OpenAI returns an index into the shortlist and the backend validates it. The prompts are recommendation.food and recommendation.item. Context and choice · Prompts
Food candidates and listings
food_candidates filters and ranks up to 12 catalog meals using goals, logged meals, preferences, and available allergen tags. After selection, food searches Shopee Food and keeps up to three distinct restaurants within budget. The restaurant prices come from the Shopee results. Food implementation
Item candidates and listings
item can suggest an eye mask for short sleep or a foam roller when recent activity meets the goal. It can use Ploy’s demo sleep or offer a general eye-mask suggestion. Shopee Mall supplies product facts. The backend takes up to four results, sorting them by rating descending and then price ascending. Item implementation
Publishing and rendering
Zippy.recommend allows one recommendation at a time per guest and guards against publishing after a guest reset. It saves item products to the session for the existing Buy route and emits a notification plus cards. The browser polls the feed and maps card kinds to UI. Push can deliver the notification to subscribed devices. Service · Feed polling · Card mapping
