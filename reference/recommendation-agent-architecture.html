Recommendation agent architecture

Both presenter actions share guest context and chat delivery. Each branch builds its own candidates and calls a different Shopee tool.

Where each decision lives

Guest and session
presenter_trigger checks the presenter key. It matches display names case-insensitively, then runs once per matching guest ID. Each run targets that guest’s most recently updated session, with presenter as the default. Presenter route · Guest lookup
Data and selection
load_recommendation_context loads the profile, persona, and meals from MongoDB by guest ID. choose uses the first candidate without a model. With a model configured, OpenAI returns an index into the shortlist and the backend validates it. The prompts are recommendation.food and recommendation.item. Context and choice · Prompts
Food candidates and listings
food_candidates filters and ranks up to 12 catalog meals using goals, logged meals, preferences, and available allergen tags. After selection, food publishes a meal. A later places request runs find_places, which takes up to three distinct restaurants, ranked by protein, distance and price, using the Shopee results. Food implementation
Item candidates and listings
item can suggest an eye mask for short sleep or a foam roller when recent activity meets the goal. With sleep data at goal, it can still frame an eye mask as optional. When no qualifying reading is available, it asks for health history through an error response. Shopee Mall supplies product facts. The backend takes up to four results, sorting them by rating descending and then price ascending. Item implementation
Publishing and rendering
Zippy.recommend allows one recommendation at a time per guest and guards against publishing after a guest reset. It saves item products to the session for the existing Buy route and emits a notification plus cards. The browser polls the feed and maps card kinds to UI. Push can deliver the notification to subscribed devices. Service · Feed polling · Card mapping

HTTP entry points

POST /presenter/trigger
Send {guest_name, agent} with X-Presenter-Key. Use food or item. The response reports trigger status and guest/device counts. The recommendations are published to the matching guests’ feeds. Presenter handler
POST /recommendations/food
Send {session_id} as the current guest. The route calls Zippy.recommend with food, publishes the meal, saves its pending restaurant query, and returns {session_id, items}. Food handler · Shared service
POST /recommendations/food/places
Send the same session_id, with optional location: {lat, lng}. Returns {text, card}, defaults to Silom, and consumes the pending query after the lookup. Returns 404 if there is no pending meal. Demo sessions use Silom. Places handler · Pending meal lookup
GET /recommendations/health-history
Optional inclusive start and end dates select wearable readings, workouts, weights, and body composition. The default is 14 days ending today, and the maximum is 90 days. The route returns only the current guest’s data and sets Cache-Control: no-store. Health history handler

Item recommendations are available through the shared presenter endpoint. There is no current guest-scoped POST /recommendations/item. Browser calls use the /api prefix through Caddy, which adds the backend token. The guest routes use the session cookie. Proxy · HTTP contract
